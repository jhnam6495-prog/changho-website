## A. 레이아웃 / 스타일 이슈

### A1. 섹션 탭 메뉴가 스크롤해도 상단에 고정되지 않음

- **증상**: 페이지를 스크롤하면 `position: sticky`로 만든 탭바가 고정되지 않고 콘텐츠와 함께 그대로 흘러가 버림
- **원인**: `globals.css`의 `html { overflow-x: hidden }`이 `body`의 overflow가 뷰포트로 전파되는 것을 막아, `body`가 "실제로는 스크롤되지 않는 별도의 스크롤 컨테이너"로 취급됨. 그 결과 `sticky` 요소의 기준이 화면(viewport)이 아니라 이 `body`가 되어버려 고정되지 않음
- **해결**: `overflow-x: hidden`을 `html`에서 제거하고 `body`에만 남김. 가로 스크롤 방지 효과는 동일하게 유지되면서 sticky가 정상 동작

헤드리스 브라우저로 실제 스크롤 후 `getBoundingClientRect()`를 측정해 재현 → 수정 후 스크롤 위치와 무관하게 `top` 값이 고정되는 것을 확인.

### A2. 인증서 PDF 미리보기 박스에서 세로 스크롤 발생

- **증상**: 좁은 화면에서 카드 안 PDF 미리보기가 넘쳐 스크롤바가 생기고, 활성 탭 밑줄과 겹쳐 보임
- **원인**: CSS `aspect-ratio` + `max-width: 100%` 조합은 폭이 줄어드는 상황에서 높이가 함께 줄지 않아, 실측 결과 비율이 `0.573`로 나와야 할 `0.707`(A4 비율)과 어긋남 — 즉 박스가 필요 이상으로 길어져 내부 콘텐츠가 넘침
- **해결**: `ResizeObserver`로 컨테이너의 실제 `clientWidth`/`clientHeight`를 측정하고, PDF 실제 규격(595.28 × 841.89pt)에 맞는 정확한 픽셀 크기를 JS에서 계산해 적용. CSS만으로 해결하지 않고 JS 실측으로 전환

### A3. 모바일에서 인증서가 아예 보이지 않음

- **증상**: 데스크톱에서는 정상 출력되던 인증서 PDF 미리보기가 모바일 브라우저에서는 빈 화면
- **원인**: 모바일 브라우저(iOS Safari, 모바일 Chrome 등)는 `<iframe>` 안에 PDF를 인라인 렌더링하는 기능을 데스크톱만큼 지원하지 않음
- **해결**: 헤드리스 크로미움으로 PDF 1페이지를 미리 스크린샷해 `.jpg`로 변환 → 카드에는 이 이미지를 표시하고, "원본 보기"만 실제 PDF 파일로 연결. 이미지는 어떤 브라우저에서도 100% 표시되므로 근본적인 해결

### A4. 대표이사 서명 줄에서 이름 중간이 줄바꿈됨

- **증상**: 모바일에서 "창호종합건설(주) 대표이사 이"까지 나오고 "진규"가 다음 줄로 넘어감
- **원인**: 회사명, 직함, 이름을 공백으로 이어 붙인 한 문단으로 처리해, 화면 폭이 좁아지면 브라우저가 임의의 공백에서 줄바꿈함
- **해결**: "회사명"과 "직함 + 이름"을 처음부터 별도 줄로 분리하고, 이름 부분에는 `white-space: nowrap`을 적용

### A5. 헤더 서브메뉴가 클릭 후에도 닫히지 않음

- **원인**: 드롭다운 표시를 순수 CSS `:hover`/`:focus-within`으로만 제어해, 클릭(선택)이라는 이벤트 자체에는 반응하지 않았음
- **해결**: JS `useState`로 열림 상태를 직접 관리(`onMouseEnter`/`onMouseLeave`)하고, 서브메뉴 링크의 `onClick`에서 명시적으로 상태를 닫음. CSS의 hover 트리거 규칙은 완전히 제거해 두 제어 방식이 충돌하지 않도록 함

### A6. 팝업 캐러셀에서 항목마다 상단 위치가 움직임

- **증상**: 홈 팝업이 공지 여러 건을 캐러셀로 보여주도록 바뀐 뒤, 다음/이전으로 넘길 때마다 팝업의 위쪽 가장자리가 위아래로 들썩임
- **원인**: 오버레이를 `alignItems: "center"`로 화면 중앙 정렬했는데, 공지마다 이미지 유무·본문 길이가 달라 팝업 카드의 전체 높이가 항목마다 다름 — 중앙 정렬 특성상 높이가 바뀌면 상단 위치도 함께 밀려남
- **해결**: 오버레이 정렬을 `alignItems: "flex-start"` + 고정 `paddingTop`(예: `8vh`)으로 바꿔, 카드 높이와 무관하게 상단 위치를 고정. 카드 자체의 `maxHeight`를 화면 하단 여유를 감안한 값(`80vh`)으로 낮춰 어떤 항목이든 화면 밖으로 넘치지 않게 함

## B. 백엔드 환경 설정 (상세)

공지사항 기능을 위해 Vercel Blob을 처음 도입하면서 실제로 겪은 순서 그대로 기록. 결과적으로 **"스토어는 Public으로, 환경변수 설정 후에는 항상 재배포"** 두 가지만 지켰어도 아래 4건은 전부 피할 수 있었다.

### B1. Blob 스토어를 Private로 생성해 업로드 전부 실패

- **증상**: 서버 500 에러
- **에러**: `Vercel Blob: Cannot use public access on a private store.`
- **원인**: Storage → Create Database → Blob으로 스토어를 만들 때 접근 모드를 별도로 확인하지 않아 기본값(Private)으로 생성됨. 코드는 방문자가 로그인 없이 첨부파일을 볼 수 있도록 모든 `put()`에 `access:'public'`을 지정하고 있어 충돌
- **확인**: 스토어 Settings 화면에 "*The access mode cannot be changed after creation.*"라고 명시 — 한번 Private로 만들면 되돌릴 수 없음
- **해결**: 기존 스토어는 폐기하고, 생성 단계에서 **Public**을 명시적으로 선택해 새로 생성

### B2. 이전 스토어가 남아있어 새 스토어를 못 찾음

- **증상**: 서버 500 에러
- **에러**: `Vercel Blob: This store does not exist.`
- **원인**: B1의 Private 스토어를 프로젝트에서 정리하지 않은 채 Public 스토어를 새로 만들어 같은 이름으로 연결 — 두 스토어가 동시에 프로젝트에 연결되며 배포가 참조하는 스토어 식별자가 꼬임
- **해결**: 예전 Private 스토어를 프로젝트 Storage 목록에서 완전히 삭제 → Public 스토어 하나만 남은 상태에서 재배포

> 교훈: 스토어 이름을 재사용하지 말고, 잘못 만든 스토어는 새로 만들기 *전에* 먼저 정리한다.

### B3. 환경변수를 추가해도 실제 배포에는 반영되지 않음

- **증상**: `ADMIN_PASSWORD`를 대시보드에 저장했는데도 로그인이 계속 실패
- **원인**: Vercel은 환경변수를 **배포 시점**에 고정한다. 값을 추가/변경해도 이미 떠 있는 배포에는 적용되지 않음
- **해결**: Deployments 탭에서 최신 배포를 **Redeploy**해야 새 값이 반영됨. 이후 절차에 "환경변수 변경 → 반드시 재배포"를 표준 단계로 고정

### B4. 첨부파일 클릭 시 다운로드가 시작되지 않음

- **증상**: 첨부파일 링크를 클릭하면 저장 대화상자 없이 그냥 이미지가 새 탭에 열림
- **원인**: 파일이 사이트와 다른 도메인(`*.public.blob.vercel-storage.com`)에 있어, HTML의 `<a download>` 속성이 브라우저 정책상 무시됨(교차 출처에서는 미동작)
- **해결**: `put()`이 반환하는 `blob.url` 대신, 강제 다운로드용으로 별도 제공되는 **`blob.downloadUrl`**을 링크에 사용

```ts
// app/lib/notices.ts
interface NoticeFile {
  name: string;
  url: string;
  downloadUrl: string;  // 다운로드는 반드시 이 값 사용
  size: number;
}
```

### B5. 공지 수정 직후에도 예전 내용이 보임

- **증상**: 제목/내용을 수정하고 저장했는데 공개 페이지에는 한동안 이전 내용이 계속 노출
- **원인**: 공지 수정은 같은 파일 경로(`notices-data/{id}.json`)를 덮어쓰는 구조인데, Blob의 CDN이 이전 응답을 기본값(최대 1개월)만큼 캐시하고 있어 "같은 URL"에 대해 예전 내용을 계속 서빙
- **해결**: ① 읽을 때 URL 끝에 `?t={timestamp}` 캐시버스팅 쿼리를 붙여 매번 새 요청으로 취급되게 함 ② 저장할 때 `cacheControlMaxAge: 60`(허용 최솟값인 1분)으로 설정해 캐시 잔존 시간 자체를 최소화

```ts
// app/lib/blob-store.ts
function bust(url: string) {
  return `${url}${url.includes("?") ? "&" : "?"}t=${Date.now()}`;
}
// 조회 시: fetch(bust(meta.url), { cache: "no-store" })
```

신규 작성은 매번 새 `id`로 새 경로를 쓰기 때문에 이 문제가 없었고, "수정" 기능을 추가하면서 처음 드러난 문제였다.

### B6. 로그인 세션 서명에 Node crypto를 쓸 수 없음

- **배경**: Next.js의 `middleware.ts`는 기본적으로 **Edge 런타임**에서 실행되며, Node.js 전용 모듈(`crypto.createHmac` 등)을 사용할 수 없음
- **해결**: Node crypto 대신 **Web Crypto API**(`crypto.subtle`)로 HMAC-SHA256 서명을 구현 — 이 API는 Edge와 Node 런타임 양쪽에서 동일하게 동작하므로 미들웨어와 서버 액션에서 같은 코드를 공유 가능

## C. 첨부파일 업로드 아키텍처 전면 재작업 (연쇄 이슈)

실사용 중 사용자가 "공지사항에서 파일 추가 시 페이지를 표시할 수 없다"고 신고하면서 시작된 재작업. 원인이 하나가 아니라 **네 겹으로 쌓여 있어서**, 하나씩 고칠 때마다 증상이 바뀌며 다음 원인이 드러났다. 최종적으로 서버 경유 업로드 자체를 폐기하고 [프레임워크 설계서 7장](./framework-spec.md#7-파일-업로드-아키텍처-필수-준수)의 구조로 전면 교체했다.

### C1. 6MB 안팎 첨부파일에서 "페이지를 표시할 수 없음"

- **증상**: 관리자가 6MB 안팎의 첨부파일을 올리면 브라우저가 아예 페이지를 못 불러옴. 초기에는 `next.config.ts`의 `experimental.serverActions.bodySizeLimit`(당초 `20mb`로 설정되어 있었음) 설정 실수로 의심했으나, 이 값을 아무리 올려도 재현됨
- **재현**: 3MB 합성 파일은 정상 업로드(303), 6MB 합성 파일은 413로 거부되는 것을 헤드리스 브라우저로 직접 확인 — 애매한 추측이 아니라 실측으로 경계값을 확정
- **진짜 원인**: Vercel 서버리스 함수는 **요청 본문 크기에 플랫폼 레벨 하드 캡(약 4.5MB)**이 있다. `bodySizeLimit`은 Next.js Server Actions 자체의 상한일 뿐, 그 요청이 결국 올라타는 Vercel 서버리스 함수의 플랫폼 캡은 애플리케이션 설정으로 바꿀 수 없음
- **해결**: Server Action이 `File`을 직접 받는 구조를 폐기하고, **브라우저가 Vercel Blob에 직접 업로드**하는 구조(`@vercel/blob/client`)로 전면 교체. Next.js 서버는 업로드가 끝난 뒤의 URL 메타데이터만 받는다. `next.config.ts`의 `bodySizeLimit` 설정은 더 이상 필요 없어져 제거함

### C2. 업로드 토큰 요청이 308 리다이렉트되며 인증 실패

- **증상**: C1을 고친 뒤에도 업로드가 계속 실패. 응답을 보니 클라이언트가 `/api/blob-upload`로 보낸 POST가 308로 `/api/blob-upload/`로 리다이렉트되고, 리다이렉트된 요청이 400으로 거부됨
- **원인**: `next.config.ts`의 `trailingSlash: true` 때문에 슬래시 없는 내부 경로로의 요청은 전부 트레일링 슬래시 버전으로 308 리다이렉트된다. 이 리다이렉트 과정에서 인증/본문 처리가 예상대로 이어지지 않아 실패로 이어짐
- **해결**: 클라이언트의 `handleUploadUrl`을 처음부터 `/api/blob-upload/`(끝 슬래시 포함)로 지정해 리다이렉트 자체를 없앰. 이 프로젝트는 내부 API 호출 경로 전반에 이 규칙을 적용해야 함

### C3. OIDC 연결 스토어에서 "No read-write token found"

- **증상**: C2를 고친 뒤 실제 에러 본문을 확인하니 `Vercel Blob: No read-write token found. Either configure the BLOB_READ_WRITE_TOKEN environment variable, or pass a token option to your calls.`
- **원인**: 이 프로젝트의 Blob 스토어는 고정 시크릿(`BLOB_READ_WRITE_TOKEN`) 없이 **OIDC**로 연결되어 있다(`BLOB_STORE_ID` + Vercel이 런타임에 주입하는 OIDC 토큰). 일반 `put()`/`list()`/`head()`/`del()`은 OIDC를 지원하는 공용 인증 경로(`requestApi`)를 쓰지만, `@vercel/blob/client`의 구식 클라이언트 토큰 발급 함수 `handleUpload()`는 `BLOB_READ_WRITE_TOKEN` 존재 여부만 확인하는 별도 코드 경로를 써서 OIDC로는 아예 동작하지 않음(SDK 자체의 한계, 2.8.0 기준)
- **해결**: `handleUpload()`/`upload()` 대신 **presigned URL 방식**(`handleUploadPresigned()` + `issueSignedToken()` + 클라이언트의 `uploadPresigned()`)으로 교체. 이 경로는 OIDC를 지원하는 공용 인증 함수를 그대로 쓰므로 정적 토큰 없이도 동작한다. 업로드 완료 콜백 서명 검증용 `BLOB_WEBHOOK_PUBLIC_KEY`는 Blob 스토어를 OIDC로 연결하면 자동으로 환경변수에 추가되어 있어 별도 설정이 필요 없었음

### C4. 한글 등 비-ASCII 파일명에서만 업로드 실패

- **증상**: C3까지 고친 뒤 영문 파일명은 잘 되는데, 한글 파일명(`(주)티제이.jpg` 등)만 `Vercel Blob: Blob path does not match the signed token scope; expected ...`로 실패. `/api/blob-upload` 라우트의 catch 블록에 로깅이 없어 처음에는 원인을 알 수 없었고, `console.error`를 추가해 Vercel 런타임 로그(`vercel logs --follow`)로 실시간 재현해서야 정확한 에러 메시지를 확보함
- **원인**: `@vercel/blob`이 presigned 토큰(delegation token)에 담긴 경로를 복원할 때 `base64UrlDecodeToString()`이 `atob()`를 우선 사용하는데, Node.js(16+)에 전역으로 존재하는 `atob()`는 base64를 **바이트 단위로만** 디코딩해 UTF-8 멀티바이트 문자를 제대로 복원하지 못한다(모지바케). 그 결과 토큰 발급 시점의 경로와 실제 업로드 요청 경로가 문자 인코딩 때문에 서로 달라져 검증에 실패 — SDK 자체의 버그
- **해결**: Blob 저장 경로를 구성할 때 파일명 부분을 `encodeURIComponent()`로 감싸 항상 ASCII로만 구성되도록 우회. 화면에 표시하는 파일명은 첨부파일 메타데이터의 `name` 필드에 원본 그대로 별도 보관하므로 사용자 경험에는 영향 없음

## D. 검증 방법론 노트

### D1. 헤드리스 브라우저 테스트 스크립트의 타이밍 함정

실제 앱 버그가 아니라 **검증 스크립트 자체의 결함**으로 오진했던 사례가 여러 번 있었다. 다음 프로젝트의 자동 검증에도 그대로 적용할 원칙:

- `page.waitForLoadState('networkidle')`만으로는 서버 액션의 리다이렉트 완료를 보장하지 못함 → 목적지 URL을 `page.waitForURL()`로 명시적으로 기다려야 신뢰 가능
- 같은 스크립트를 개발 서버가 **Fast Refresh로 재컴파일 중**일 때 실행하면 클릭이 엉뚱한 결과로 이어질 수 있음 — 서버가 안정된 뒤 재검증해서 재현되는지 확인
- `curl`로 Next.js 페이지를 확인할 때, 응답이 React 서버 컴포넌트 스트리밍 페이로드(RSC)인 경우 일반 정규식 파싱은 신뢰할 수 없음 — 렌더링된 DOM(`innerText`) 기준으로 최종 확인
- 인프라 캐시 지연(B5)과 스크립트 타이밍 결함은 증상이 비슷하므로, 코드를 고치기 전에 **어느 쪽이 원인인지 먼저 격리**해서 재현한다
- 서버 라우트의 `catch` 블록은 **처음부터 `console.error`로 로깅**해 둔다. 그렇지 않으면 클라이언트에 표시되는 뭉뚱그려진 에러 메시지(예: "Failed to retrieve the presigned URL")만으로는 원인을 좁힐 수 없고, `vercel logs --follow`로 실시간 재현해야만 진짜 원인이 드러난다(C4 사례)

### D2. 로컬 개발 서버는 Blob 데이터를 읽거나 쓸 수 없음

- **증상**: `next dev`로 로컬에서 관리자 로그인 후 게시물을 작성해도 목록에 아무것도 안 뜸(`등록된 공지 (0)`). Server Action 자체는 에러 없이 리다이렉트까지 성공하는 것처럼 보여 처음에는 원인을 특정하기 어려웠음
- **원인**: 이 프로젝트의 Blob OIDC 연결은 **Production/Preview 환경에만 활성화**되어 있고 Development 환경에는 연결되어 있지 않다. `vercel env pull`로 로컬에 내려받는 `VERCEL_OIDC_TOKEN`은 `--environment production`을 지정해도 **항상 `environment:development`로 스코프된 토큰**이 발급되며, 이 토큰으로 Blob에 접근하면 `Vercel Blob: OIDC is enabled for this project, but not for the "development" environment.`로 거부된다. `ADMIN_PASSWORD`/`SESSION_SECRET`도 Vercel이 "Sensitive" 값으로 표시해 `env pull`로는 빈 문자열만 내려받아짐(별도로 알고 있는 값을 `.env.local`에 직접 채워 넣어야 로그인 자체는 로컬에서도 테스트 가능)
- **해결**: 로컬 개발 서버로는 UI 레이아웃·정적 페이지 확인까지만 하고, **CMS 작성/수정/삭제와 파일 업로드가 걸린 기능은 항상 배포 후 프로덕션에서 헤드리스 브라우저로 검증**한다. 다행히 이 프로젝트는 이미 실제 데이터(예: "홈페이지 팝업 노출"로 지정된 기존 공지 여러 건)가 쌓여 있어, 검증용으로 새 테스트 데이터를 만들지 않고 기존 데이터를 그대로 활용할 수 있는 경우가 많다

## E. 다음 프로젝트를 위한 사전 체크리스트

- [ ] Blob 스토어는 **생성 단계에서부터 Public**으로 선택한다 (생성 후 변경 불가)
- [ ] 스토어를 다시 만들어야 한다면, 새로 만들기 **전에** 기존 스토어를 프로젝트에서 정리한다
- [ ] 환경변수를 추가/변경한 뒤에는 **반드시 Redeploy**한다
- [ ] `html`이 아니라 `body`에만 `overflow-x: hidden`을 건다
- [ ] PDF 첨부는 처음부터 "이미지 미리보기 + 원본 PDF 링크" 2단 구조로 설계한다
- [ ] 같은 경로를 덮어쓰는 데이터(게시물 수정 등)는 캐시버스팅과 `cacheControlMaxAge` 최소화를 처음부터 넣는다
- [ ] Blob 첨부파일 다운로드 링크는 `url`이 아니라 `downloadUrl`을 쓴다
- [ ] 미들웨어에서 서명/암호화가 필요하면 Node `crypto`가 아니라 Web Crypto API를 쓴다
- [ ] **파일 업로드는 처음부터 클라이언트→Blob 직접 업로드(presigned URL)로 설계한다.** Server Action이 `File`을 직접 받는 구조는 Vercel의 ~4.5MB 플랫폼 캡 때문에 처음부터 표준에서 제외한다 (C1~C4, 프레임워크 설계서 7장)
- [ ] 내부 API 라우트 URL은 `trailingSlash: true` 설정과 항상 끝 슬래시를 맞춘다
- [ ] Blob 저장 경로의 파일명 부분은 `encodeURIComponent`로 감싼다 (한글 파일명 대비)
- [ ] 서버 라우트의 `catch` 블록에는 처음부터 `console.error` 로깅을 넣는다
- [ ] 항목마다 높이가 다른 콘텐츠를 순차 노출하는 팝업/모달은 중앙 정렬이 아니라 상단 고정 정렬로 설계한다
- [ ] CMS·업로드 관련 기능은 로컬이 아니라 **배포 후 프로덕션**에서 검증한다는 것을 처음부터 팀에 공유한다
